This is summarisePending() again. The documents reminder already solved “one line, several kinds”: one kind — name it; several — count them. Same rule, same place to put it, and the web gets it for free.
⚠️ The sub-line always carries the split, even when the headline names one kind — because “3 owed a call” still needs to say how many are late.
⑥Intent, not record
⚠️ THE SAME WORD, POINTING OPPOSITE WAYS
“reminderKind: 'CALL' is an INTENT — remind me to call them on Tuesday. A CustomerActivity of type CALL is a RECORD — I called them. Same word, opposite direction in time.”
packages/shared/src/crm/reminder.ts
And the rule that follows, in the same file: “a reminder row must always render its reason.”
So every row on this card leads with the verb and carries Reminder · call underneath. Never the client name alone with a number beside it — that is a list, and a list of names is what somebody has to open a screen to understand.

⚠️ MEETING is deliberately not a reason. “A meeting is real work that somebody is assigned and turns up to — that is a Task, not a nag.” If the widget ever offers it, the fix is a job, not a reminder.
⑨Whose book
WHOSE BOOK
view: 'all'The whole book. A reminder on any client reaches you if you manage them.
view: 'own'Only clients you manage. managerIds contains you.
view: 'none'No card. And no request — the member never pays for a book they may not read.
⚠️ §3.11’s two warnings, both verified in packages/shared/src/types/permissions.ts:
resolveCrmCaps( systemRole: string | null, permissions: PermissionSet // flat. no spaces. )
1 · CRM caps resolve off the ORG role only. A space-scoped sales role grants nothing while looking configured.
2 · legacyViewAll = !!p.canViewAllTasks maps straight to view: 'all'. Grant a sales role “view all tasks” and you have handed over the whole client book.
⑦The row is the act

⑪The All row
THE WAY THROUGH IS ALWAYS THERE
All 214 clients › is on every state of this card. Not when the list is empty, not when it is full — always.
The book is the reason the module was bought. A card that only surfaces on the days somebody is late hides it most of the time.
It is the one part of the card that does not depend on data arriving. Empty, loading, offline, refused — the row is there and it works.
And it is what makes the card safe to make small: everything the three sections cannot hold is one tap away, by the same door, in the same place, every time.
⚠️ The count comes from the same response as the rest. If it has not arrived, the row still renders — All clients ›, without a number. A door that waits for a number is not a door.
⑩What is actually there
MEASURED IN THE REPO
01⚠️ There is no endpoint that can answer this widget.Activities — and therefore reminders — are read per customer: GET /customers/:id/activities. customers.controller.ts has no cross-customer feed. Answering “who is owed a call?” for a 214-client book means 214 requests. §3.11 is marked Cost B; it is C.
02And “going cold” is not computable either.GET /customers returns name, type, status, managerIds, contactOf, createdAt — no last-touched date. The second half of §3.11’s question needs the same new endpoint as the first.
03The endpoint to build.GET /crm/due?limit=5 → [{ customerId, name, type, reminderKind, reason, dueAt, assigneeId, managerCount, lastTouchedAt }]. One indexed read over CustomerActivity where type = REMINDER and doneAt is null, narrowed by the caller’s CRM view, plus the cold tail. It is also what the /customers screen wants for its own “today” tab.
04⚠️ Never grant a sales role canViewAllTasks.resolveCrmCaps: legacyViewAll = !!p.canViewAllTasks → view: 'all'. The whole client book, silently. And CRM caps resolve off the ORG role only, so a space-scoped sales role grants nothing while looking configured. Both of §3.11’s warnings check out.
05isContact and isPortalResident are not clients.“A person who works at a company — NOT a client, and never billed as one.” And a resident is “somebody’s tenant with an app login”. Neither belongs in a count of who owes you a call.
Everything else is already there: the reminder columns, the shared reason rules, managerIds, crmCaps, and updateActivity to mark one done. One endpoint stands between this card and shipping.
